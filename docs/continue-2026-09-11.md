## push 后 CI 抓到的真缺陷（v0.13.0 之外，但值得记档）

`单元测试 ✓ / 线上冒烟 ✗ / 落库同步 ✓ / 复盘闭环 ✓ / 开奖推送 skipped`（skipped 是对的：notify 只在 schedule/dispatch 后跑）。

冒烟红在第三个端点：`curl -m 30 /api/ssq/latest` 超时。本机复现三次：**25s 超时 / 22.2s 成功 / 2.4s 命中缓存** —— 根因是**所有上游 fetch 都没有超时**（`fetch500`、`fetchCWL` 两步、`fetch17500`、`fetchSmall`、自定义源共 8 处），而境内站点从 CF 边缘 PoP 访问偶尔直接不回包。这不是 v0.13 引入的，是它把 CI 频率提上去之后才暴露的。

修法：`worker/src/net.js` 的 `fetchT(url, opts, ms)`，两档 `UPSTREAM_MS=8000` / `BULK_MS=20000`（17500 的全量文本约 0.5MB，回测要用，宁可多等也别轻易降级）。超时抛 `TimeoutError`，正好被既有的 `.catch` 接住并按多源设计降级。

**变异教训**：把 `signal` 去掉后，`net.test.mjs` 第 2 项不是变红而是**永远挂着**（node --test 默认没有单测超时）——第一次做这个变异直接把命令拖到超时、留下两个僵尸 node 进程。给用例加 `{ timeout: 5000 }` 之后，同样的变异在 5 秒时报 `test timed out after 5000ms`。**「会挂」的测试和「没有」的测试一样危险**，尤其当它守的正是「别挂」这件事。

### 第二个红：备份导出与冒烟并发，`/api/review` 返回 500

`cd63272` 那次 push 的 CI：单元测试 ✓ 落库 ✓ 复盘 ✓，但冒烟红在第五个端点 `review: HTTP 500`（不是超时）。时间线对得上——备份 workflow 的导出正是那 25 秒在跑（22:38:50 → 22:39:14），而 wrangler 导出前的警告原文就是「during which your D1 database **will be unavailable to serve queries**」。备份结束后同一端点立刻 200（12 行，实测）。

处置：`backup.yml` 与 `sync.yml` 共用 concurrency 组 `lottery-prod`、`cancel-in-progress: false`（落库跑一半被掐掉比排队更糟）。定时上两者本来错开（备份北京 00:00 / 落库 21:20–21:40），这条防的是手动 dispatch 撞车。

## 本轮确立的事实（都有命令输出，别重复验证）

1. **测试数 106 = 89 worker + 12 统计内核 + 5 推送**（逐文件实测：unit 34 / predict 26 / coldness 8 / review 5 / verify-batch 9 / ui-render 4 / net 3 / stats 12 / notify 5）。README 与 sync.yml 都按这个写。
2. **tickets 传字符串会炸**：`verifyBatch(kind, draws, "01 02 ...", ...)` → `TypeError: (tickets || []).map is not a function`（实测打印过）。因此路由在**取数之前**用 `Array.isArray` 拦成 400——取数要打外部源（墙钟 1–4s），空请求不该白跑。
3. **`wrangler d1 export` 会把预签名 R2 链接打到 stdout**，含 `X-Amz-Credential` / `X-Amz-Signature`，1 小时内可直接下载整库；公开仓库的 Actions 日志人人可读 → backup.yml 把输出重定向后 `grep -v r2.cloudflarestorage.com` 再打印。
4. **真库导出实测**：`lottery` 库 → 173 KB / 1007 条 INSERT / 6 表；还原到内存 sqlite 后行数 `small_draws 729 / draws 120 / dlt_draws 120 / predlog 12 / sync_log 23 / favs 0`（合计 1004）。
5. **导出 SQL 的 `CREATE TABLE` 不带 `IF NOT EXISTS`**：往已有同名表的库里再导一次 → `table draws already exists`（实测）。所以恢复姿势只有两种：恢复到**新库**，或导出时加 `--no-schema` 只灌数据。docs/BACKUP.md 按这个写。
6. **线上 `/api/meta` 的字段**：`stale[]` 有 `days===0` 可用来判定「今天真开了奖」；`dlt` 的 `/api/dlt/latest` 里 `date` 仍为 `""`（500 解析器不给日期，D1 里有）→ **推送取数一律用 meta 的 date，不用 latest 的 date**。
7. **冒烟与 review job 不受本轮影响**：sync.yml 的 job 列表 test/smoke/review/sync/notify。

## 三个关键取舍（为什么这么做，防止下一个人"顺手改掉"）

- **金额宁缺毋假**：`FIXED` 只收录能站住的固定奖（ssq 三~六等、3D/排列3 直选组选、快乐8 查表）；ssq 一二等是浮动奖、dlt 固定奖在 2026-02-02 换过规则（证据 `docs/coldness-dlt-2026-09.md` 的奖金包分簇）、qlc/pl5/qxc 未逐字段校验 → **全部 `amount: null`**，前端渲染成「—（见公告）」并给「另有 N 注中的是本站未给金额的奖级」告警。错的金额比没有金额更糟：用户从此不信它的任何输出。
- **前后端契约测试**（`ui-render.test.mjs`）：前端内联脚本不能 import，用 `node:vm` + 最小 DOM 桩把整段脚本灌进去取 `renderVerifyBatch` 引用，再喂**真后端**（同仓库 `verifyBatch`）的响应做断言。存在的理由：`esc(undefined)` 渲染成空串，字段改名（`amountKnown` 等）在页面上是**静默消失**，不会报错。两类变异都验证过会变红：① 金额 null 改成 `w.amount || 0` → 2 项红；② `s.amountKnown` 改成 `s.amountXKnown` → 1 项红（"汇总行要显示后端算好的已知金额"）。
- **推送做在 Actions、且失败也发**：Workers 免费层的 `waitUntil` 会静默丢（v0.12 刚为此付出过"闭环死了五天 CI 全绿"的代价）。notify job 的 `needs: [sync, review]` + `if: !cancelled()`，job 挂了标题变 ❌；只在 `schedule` / `workflow_dispatch` 触发，否则每次代码 push 都会往群里发一条。

## 环境坑（本轮新增/复发的）

- **`node -e` 里用 `subprocess.run(['bash',...])` 会命中 WSL 的 `/bin/bash`（本机 WSL 无发行版）→ 全部"语法错误"假象。** 校验 workflow 里的 run 块：用 python 把每块抽成 `.sh` 文件，再在 Git Bash 里 `bash -n` 逐个查（本轮 18 块全 OK）。
- python 往 stdout 打中文会被 GBK 编码卡死 → 结果写文件再 Read，或只打 ASCII。
- `wrangler.cmd` 在这个 shell 里直接调会报 `'node' 不是内部或外部命令` → 用 `node <...>/wrangler/wrangler-dist/cli.js`。
- 本机无 `sqlite3` CLI，但 bundled node 有 `node:sqlite`：`--experimental-sqlite` + `DatabaseSync` 即可在本地真跑一遍「导出→还原→逐表计数」，backup.yml 的验证逻辑因此可离线复现。
- 同文件多 Edit 并行会互相覆盖（老坑，本轮全程串行 + 每次 grep 复验，未复发）。
